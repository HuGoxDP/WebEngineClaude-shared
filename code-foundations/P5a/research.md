## Decisions (with evidence)

1. **Postgres is backed up logically (`pg_dump`), volumes by copy.** A tar of a live
   `pgdata` directory is not crash-consistent; a dump is. The archives/assets/previews volumes
   are content-addressed append-only stores (the backend never rewrites a stored object — the
   whole addressing scheme assumes it), so a read-only copy is consistent enough, and the
   restore restores the copy plus the dump.
2. **A `backup` service in the main compose, not a host cron.** A service keeps the whole
   procedure in the repo (what runs, on what schedule, with what retention), runs on the same
   network and volumes as the stack, and is what a production host reuses. Schedule = a loop
   (`sleep ${BACKUP_SCHEDULE_HOURS:-24}`, backup first on start), no cron daemon inside the
   image. Retention: keep the newest `BACKUP_KEEP_DAYS` (default 14) of timestamped backup
   directories.
3. **The retention/naming logic is a dependency-free Node module (`backup/retention.mjs`)**,
   unit-tested with `node --test` like the rest of the repo — the pruning rules are the part
   worth pinning (boundary day, missing/garbage entries, keep-at-least-one).
4. **The restore is a script with a dry-run default and a written procedure**
   (`docs/backup-restore.md`) that is *actually run once on a scratch stack* (a second compose
   project, fresh volumes) and its output recorded — that is the row's acceptance, not just a
   script that exists. Restoring the live stack is never the default.
5. **HTTPS is a compose override (`docker-compose.https.yml`) + nginx server block + a
   self-signed cert generated by a documented script** — local proof only: `curl -k
   https://127.0.0.1:<port>/api/health` answers and the CSP headers still apply. The real
   certificate and the production host are P5b.
6. **Nothing in `docker-compose.test.yml` changes** — the DB tests keep their stack; the backup
   service and the HTTPS override only ever run in the main compose, under `vl-db.lock`.

## Risks

- The VL backend integration tests need the Docker stack; they run inside `vl-db.lock`, so this
  task holds that lock for its whole build+debug phase (it is the natural owner of it).
- `pg_dump` against `database` needs the password: the backup service joins the compose network
  and reads `PGPASSWORD` from the same `.env` (env_file), like the backend does.
